# M1-3 spike notes: three offset bands per side

Code: `spike/` (throwaway, standalone page, not in the app build). Run `npx vite`, open `/spike/index.html`.
Area: downtown Burbank, San Fernando Blvd / Glenoaks Blvd. 10 blocks, 16 m to 160 m, including the shortest real blocks (44 m).

## Values that worked (zoom 17)

| Setting | Value | Notes |
| --- | --- | --- |
| Band offsets from centerline | 2, 4, 6 px | first offset 2 px, step 2 px (chosen setting, now the spike's default) |
| Band width | 1 px | the minimum below overrides it, so bands draw 2 px wide at z17 |
| Minimum band width | 2 px | MapLibre rejects `max()` around a zoom curve; clamp the minimum into each interpolate stop |
| Gap between bands | none | step equals the drawn width, so the three bands touch and read as one 6 px stripe split into three colors |
| Base end trim | 0 m | the angle trim below still applies at junctions |
| Angle trim | `reach / tan(theta/2)` | `reach` = outer band edge in metres (about 3.5 m here); theta = smallest angle to another block at that node |
| Trim cap | 35% of the block per end | keeps a stub of band on the shortest blocks |

- Offsets and widths are written at z17 and scale 2x per zoom between z15 and z19 (`interpolate`, `exponential 2`). That keeps bands a fixed distance from the street in metres, so the trim in metres stays valid at any of those zooms. At z17 one pixel is about 0.49 m.
- Sides: `line-offset` is positive to the right of the line's direction. The spike picked the street's side pair from its overall compass direction (more east-west gives N/S, otherwise E/W) as a stand-in; the real build stores `L`/`R` instead (see decision 1). The sign is `+1` for `R` and `-1` for `L`, with no direction lookup. Because `line-offset` cannot take a per-feature sign inside a zoom curve, each band is drawn as two layers (sign `+1`, sign `-1`), filtered on a `sgn` property.
- Earlier settings that also worked: 4/4/3 px width with a 4 m base trim (bands about 1 px apart), and 5/5/3.5 px (easier to read on a desktop). The smaller the offsets, the less trim the angle rule asks for, so the fork overlap described below shrinks with them, but it does not go away.
- Band colors used: `#d95f02`, `#1b9e77`, `#7570b3`. All three stay distinct next to each other.

## Result

- **Single blocks and 90 degree corners:** bands stay separate. The 44 m block, and the 58 m blocks beside it, show three clear bands per side at z17.
- **Fixed-metre trim is not enough.** A flat 9 m trim still crossed at acute corners. Trim has to grow as the angle between blocks shrinks.
- **Fails: forks and dual carriageways.** San Fernando and Glenoaks split into two one-way roads about 10 m apart, joined by 9 to 16 m slivers. At a 15 degree fork the trim needed is about 49 m, but the cap allows 20 m on a 58 m block, so the facing sides still cross. No offset or width setting fixes that, since the bands are wider than the gap between the roads.
- **Slivers (9 to 16 m)** keep only a few pixels of band after trimming. They are readable only at z18 and above.

## Decisions this forces (M2-4 and M2-5 were already done; the follow-on work is tasks M2-6, M2-8 and M3-10 in PLAN.md)

1. **DECIDED: sides are stored as `L`/`R`, relative to each segment's direction, not as N/S/E/W.** The city's directions are set from a center point at Olive Avenue and the I-5 freeway (between Ikea Way/First Street and Front Street), and the grid is offset about 45 degrees from true compass, so blocks that run NW-SE or NE-SW on a compass are plain E-W or N-S in the city's terms. Mapping each block to a city-grid side would need a measured rotation angle, a tie-break rule near 45 degrees and per-street overrides, and every rule row would inherit any error in them. `L` and `R` are defined by the line itself: facing from the first coordinate to the last in the frozen `segments.geojson`, `L` is on the left. They match MapLibre's `line-offset` directly (positive is right), so the spike's compass-to-sign step goes away. The segments file is frozen, so the direction, and therefore every L/R row, stays stable. A deliberate re-extraction must report any segment whose direction changed. Cardinal labels (city-grid) can be derived later for display in the click-through list; they are not stored. The authoring README says what `L`/`R` mean. The code change is task M2-6 in PLAN.md; the build script still reads N/S/E/W until then.
2. **DECIDED: on forks and dual carriageways, draw only the outer-facing side.** A side is inner-facing when another block lies on that side within 10 m and within 25 degrees of parallel (undirected, so opposite one-way directions count). Inner-facing sides are not drawn but stay in the click-through list. Rejected: shrinking offsets by the gap (the bands are wider than the gap, so no setting fixes it) and leaving the overlap (it looks broken on the downtown blocks). The 10 m and 25 degree values are starting values. The overlap length, whole-side versus partial hiding, high-zoom reveal, a map hint, the order against decision 4 and the other details are listed in [data-dependent-decisions.md](data-dependent-decisions.md) and are revisited in task M6-4 once real data exists.
3. **DECIDED: band trim is computed in the build script (task M2-8) and written to a generated file; the browser only reads it.** Trim needs the node graph (which blocks meet at each end, and at what angle), and the build script already has the whole segments file. For each segment end, the script finds the smallest angle theta to any other block at that node. It then sets trim = `reach / tan(theta/2)`, capped at 35% of the block per end. `reach` is the outer band edge in metres, taken from the band offsets and widths. The result is stored as `trim_start_m` and `trim_end_m` per segment in a generated file such as `data/<city_id>/trim.json`. It is not written into `segments.geojson`, which is frozen. The map layers cut each band by these values and do no geometry of their own. The values depend on the band offsets and widths, so the build script reads them from one shared config and the output is regenerated whenever either changes. The script is written test-first. The tests cover a 90 degree corner, an acute fork that hits the cap, and a sliver. The same node-graph pass can also produce the inner-facing flags for decision 2, so both come from one traversal. The cap and the per-end angle rule are tracked as row 11 in [data-dependent-decisions.md](data-dependent-decisions.md).
4. **DECIDED: blocks under about 20 m ("slivers") are not drawn as bands, unless a rule row references them.** The spike showed 9 to 16 m slivers keep only a few pixels of band after trim and read only at z18 and above. The shortest real block was 44 m, so 20 m sits well inside the gap. Slivers join the two carriageways of a fork and run across them, so decision 2 does not catch them. The build script (task M2-8) sets `sliver: true` per segment in the same generated file as the trim values (`data/<city_id>/trim.json`), not in `segments.geojson`, which is frozen. The layers draw a flagged segment only if it has a rule row; the browser makes that check, so adding a rule never needs a rebuild. A skipped sliver stays in the click-through list. Order in the build script: flag slivers first, then ignore their edges when finding theta for trim (decision 3) and the neighbours for inner-facing sides (decision 2), then compute both. The edges stay in the node graph, they just do not count. Otherwise a long block is trimmed hard for a band that is not drawn, or a side is marked inner-facing because of a block that is not on the map. Rejected: merging slivers into a neighbour (it changes which segment a rule row belongs to, has to reconcile `L`/`R` between blocks that can run in opposite directions, and forces trim to be recomputed on the merged shape). If real data shows a sliver that must be drawn and cannot be, a merge limited to two collinear blocks (under about 15 degrees apart) at a node with exactly two blocks can be added then. The 20 m value and the order are tracked as rows 8 and 12 in [data-dependent-decisions.md](data-dependent-decisions.md) and are revisited in task M6-4.
